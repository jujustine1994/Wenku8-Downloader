19. ~~**偶發下載失敗的真正原因是 HTTP 429（伺服器限流）**~~ **（2026-09-21 已修，見 `src/ratelimit.py`）**
    — 以下保留當初的診斷紀錄。

    **證據：** 該次任務 `=== 12:48:50 下載 Re:从零开始的异世界生活 | 57卷 |
    retry:3x ===`，log 裡 `HTTP 429` 出現 115 次、`HTTP 403` 5 次。
    失敗行長這樣：

    ```
    [12:51:48] [ERROR] vid=179061 charset=utf-8 -> HTTPError: HTTP 429 | 重試 3/3
    ```

    **為什麼手動下載從來不會遇到：** 429 = Too Many Requests。人工點下載
    有幾秒到幾分鐘的間隔，永遠碰不到門檻；工具是連續打。57 卷在約 3 分鐘內
    跑完 ≈ 每卷 3 秒，而 `run_download_all()` **卷與卷之間完全沒有延遲**
    （`downloader.py` 裡的 `time.sleep` 只有兩處，都在 retry 迴圈內）。

    **目前的重試邏輯會讓情況更糟：** `_fetch_bytes()` 對所有例外一視同仁，
    固定睡 `retry_delay`（預設 2 秒）就重試。對 429 來說 2 秒遠遠不夠，
    等於持續敲門讓限流一直續命。無限重試模式更明顯——log 可以看到同一個 vid
    每 2 秒撞一次 429，連續 5、6 次。

    **已採用的做法：**
    - **429 要跟其他錯誤分開處理**，不能共用 `retry_delay`。指數退避
      （2→4→8→16…）比固定間隔合理
    - **有 `Retry-After` header 就照它睡**，那是伺服器明講的等待時間
    - **退避要是整批層級，不是單卷層級**。限流是全域的，現在每一卷各自
      燒掉自己的 retry 次數去撞同一道牆，撞完就標記失敗進修復清單——
      修復流程再撞一次。碰到 429 應該讓整批停下來冷卻
    - **卷與卷之間加一點間隔**（1–3 秒），成本極低，最接近手動下載的行為
    - ⚠ 別只把 `retry_delay` 預設值調大，那會連帶拖慢所有非 429 的重試

    **順帶發現：** log 裡有 1689 行的 status 是空的（`HTTP ` 後面沒數字），
    代表 `_extract_status()` 對那些例外取不到 status code。多半是
    `_fetch_bytes()` 自己丟的 `ValueError("Response is HTML error page")`
    這類非 HTTP 例外。如果 429 有時是以錯誤頁而非 429 狀態碼回來，那這批
    也可能混著限流，值得一併查
